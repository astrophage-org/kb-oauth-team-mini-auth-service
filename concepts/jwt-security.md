# JWT Cryptographic Design and Security

This document details the cryptographic design, signature mechanisms, and credential security strategies implemented in the Mini AuthService microservice. It focuses on the JSON Web Token (JWT) lifecycle, the application of the HS256 symmetric signing algorithm, and the operational security practices required to protect cryptographic secrets and user credentials.

---

## The Cryptographic Base: HS256 Signing Algorithm

The Mini AuthService secures identity assertions using **HS256 (HMAC with SHA-256)**, a symmetric cryptographic algorithm. 

```
                                 +-----------------------+
                                 |  JWT Secret Key       |
                                 |  (Symmetric Shared)   |
                                 +-----------+-----------+
                                             |
                                             v
+-------------------+            +-----------+-----------+            +-------------------+
|     JWT Header    | ---------> |                       | ---------> |  Signed Token     |
|         +         |            |  HMAC-SHA256 Engine   |            |  Header.Payload   |
|    JWT Payload    | ---------> |                       |            |    .Signature     |
+-------------------+            +-----------------------+            +-------------------+
```

### Symmetric vs. Asymmetric Signature Schemes
In a symmetric system, the same private key is used for both generating (signing) and validating (verifying) the token. 

* **How HS256 works in this service**: The authentication microservice signs the token with a key defined in `settings.JWT_SECRET`. When a subsequent request arrives, the service uses that same secret to verify the signature integrity.
* **Architectural Rationale**: For a localized microservice architecture where token generation and token validation are handled by the same service boundaries, symmetric signing offers minimal overhead and high execution performance. The detailed trade-offs of this scheme versus asymmetric algorithms (like RS256) are explored in [[decisions/symmetric-vs-asymmetric-signing]].

## Token Structure and Claim Design

Every issued JWT consists of three base64url-encoded parts separated by dots: `Header.Payload.Signature`.

### 1. Header
The header defines the metadata for the token, specifying the algorithm used for the signature and the token type:
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

### 2. Payload (Claims)
The payload contains the statement claims about the user. The microservice relies on a stateless session context, meaning no sessions are stored in a database; instead, context is derived directly from these verified claims (see [[concepts/stateless-sessions]]).

The basic structure used by our service includes:
* **`sub` (Subject)**: Identifies the principal (the authenticated username).
* **`exp` (Expiration Time)**: A Unix timestamp defining the precise moment the token becomes invalid.

Example decoded payload:
```json
{
  "sub": "admin",
  "exp": 1716216900
}
```

### 3. Signature
The signature is generated by combining the encoded header, the encoded payload, and the secret key using the HMAC-SHA-256 hashing function:
```
HMACSHA256(
  base64UrlEncode(header) + "." +
  base64UrlEncode(payload),
  JWT_SECRET
)
```

## Cryptographic Operations in `src/auth.py`

The core authentication engine implemented in [[entities/src-auth]] handles the programmatic compilation and decompression of these cryptographic operations.

### Token Issuance Flow

```python
import jwt
from datetime import datetime, timedelta
from .config import settings

def create_access_token(data: dict, expires_delta: timedelta = None):
    to_encode = data.copy()
    # Define cryptographic validity boundaries
    expire = datetime.utcnow() + (expires_delta or timedelta(minutes=15))
    to_encode.update({"exp": expire})
    
    # Encrypt and package using PyJWT
    return jwt.encode(to_encode, settings.JWT_SECRET, algorithm=settings.ALGORITHM)
```

During this flow, `jwt.encode` takes the Python dictionary, updates it with the `exp` timestamp, executes base64url serialization, and runs the `HS256` hashing algorithm against the secret resolved from [[entities/src-config]].

### Token Verification Flow

The validation phase is critical to protecting protected routes. The incoming raw bearer token is parsed and run through PyJWT's signature validation logic:

```python
def verify_token(token: str):
    try:
        # Explicit algorithm declaration prevents algorithm-stripping attacks
        payload = jwt.decode(token, settings.JWT_SECRET, algorithms=[settings.ALGORITHM])
        return payload
    except Exception:
        # Returns None on expired tokens, bad signatures, or structural malformations
        return None
```

This verification logic is utilized directly by FastAPI's dependency injection container to protect endpoints, as detailed in [[concepts/fastapi-dependency-injection]]. For sequential request-response modeling, see [[concepts/authentication-flows]].

## Security Mitigations and Hardening Strategies

Using JWTs with symmetric keys presents unique security risks. The following mitigations are applied or recommended to secure the system:

### 1. Hardening Secret Key Storage
* **Vulnerability**: If `JWT_SECRET` is leaked or stored in plain-text code, an attacker can forge any arbitrary token, completely bypassing authentication.
* **Current Implementation**: Currently defined inside class `Settings` inside [[entities/src-config]] as a fallback fallback.
* **Hardening Path**: Upgrading the service to 12-factor compliance by loading secrets strictly from the system environment or a secrets vault using Pydantic Settings, as mapped in [[concepts/configuration-management]].

### 2. Defending Against Algorithm-Stripping ("Alg: None") Attacks
* **Vulnerability**: Older or poorly configured JWT libraries parsed the user-supplied header parameter `"alg": "None"` to bypass cryptographic verification entirely.
* **Mitigation**: The validation logic in `verify_token` explicitly locks down validation using a hardcoded configuration check: `algorithms=[settings.ALGORITHM]`. This forces PyJWT to reject any token that does not strictly employ the designated `HS256` scheme.

### 3. Credential Storage Security
The current prototype logic in `src/auth.py` compares incoming credentials to hardcoded, plain-text variables:
```python
def authenticate_user(username: str, password: str):
    if username == "admin" and password == "secret123":
        return {"username": "admin", "role": "admin"}
    return None
```
* **Production Path**: This must be migrated to an external relational database utilizing modern hashing techniques. Plain-text checks must be replaced by Argon2id password hash comparisons to ensure credential leakage from database dumps is virtually impossible. This architectural upgrade is outlined in [[decisions/database-credential-storage]].

### 4. Mitigating Stateless Revocation Issues
* **Vulnerability**: Once a JWT is signed and issued, it remains valid until its `exp` boundary is crossed. There is no natural way to revoke a compromised token early in a stateless framework.
* **Mitigations**:
  * **Short Lifecycles**: Tokens are restricted to a default lifetime of 15 minutes.
  * **Refresh Token Rotation**: Deploying a secure token system using split lifecycles, passing short-term access tokens via headers and rotation keys via `HTTPOnly` cookies (see [[decisions/token-lifecycle-refresh]] and [[decisions/stateless-session-tradeoff]]).
